# Engineering assessment: can Hooray replace Xray?

**Decision, 2026-11-20:** keep the Rust scanner and qualify one repository workflow end to end before committing to a cutover. Hooray already produces useful inventories, findings and policy decisions. The repository does not yet demonstrate equivalent detection, artifact enforcement or production capacity. A rewrite would discard the best evidence we have: the existing parser, policy, report and failure-path tests.

## What was reviewed

The starting point was [upstream main at 0361fda](https://github.com/openhoo/hooray/tree/0361fda09da6d49d477b127a64624e52aef3969e), October 13, 2026. It was five commits beyond the latest published [v0.9.0](https://github.com/openhoo/hooray/releases/tag/v0.9.0), September 22. The remote `release/v0.10.0` branch was release preparation. Its version number is not evidence of a published binary.

The base passed 838 tests, but a fresh dependency-policy run blocked it: 22 vulnerability diagnostics, one unsoundness diagnostic and one unmaintained dependency (some advisories affected multiple locked versions). A historic green CI run did not cover later advisory changes.

The base contained 58 Rust files under `src/` (60,919 lines **including inline tests**), 15 Rust integration test files (5,108 lines) and a 571-line benchmark. We followed the CLI, HTTP and monitor entry points into input, evidence, policy, persistence and rendering; inspected migrations, CI, release packaging and test fixtures; and ran the pinned toolchain locally. This is an engineering review of the project, not a claim that every rule is correct.

## Current architecture and constraints

| Area | What to keep | What matters for the next design |
| --- | --- | --- |
| Input and inventory | The [input registry](../src/input.rs) and [ecosystem parsers](../src/parsers/) produce one inventory model. SBOM, archive and image inputs have bounds; image layers have explicit whiteout handling. | A manifest declaration can be a range, whereas a lockfile can identify an installed version. There is no image OS-package database reader for dpkg, APK or RPM. [Image selection](../src/parsers/image.rs) prefers Linux/amd64 and otherwise picks a fallback; scanning one manifest does not cover an entire image index. |
| Detection and enrichment | [OSV](../src/osv.rs) batches and deduplicates requests, bounds pagination and response sizes, and limits concurrent detail requests per scan. Findings carry evidence and applicability. | Offline skips the advisory lookup. There is no versioned offline advisory snapshot. The local [SAST and file scanners](../src/scanners/) implement selected syntax and content rules; they do not establish program-wide reachability or malware feed coverage. Concurrent scans share no service-wide OSV request budget. Measure missed findings, extra findings and unknowns separately. |
| Scan orchestration | [Engine](../src/engine.rs) and [API](../src/api.rs) share risk helpers and report finalization; policies and report models have explicit validation. | CLI inputs include files; HTTP submission accepts a normalized inventory. The two drivers still orchestrate several enrichment steps separately. Extract one inventory-evaluation operation only after contract tests compare the shared output and explicitly allow file-only differences. |
| Identity and history | [SQLite](../migrations/001_init.sql) stores canonical reports and normalized lookup tables; history and diffs are useful locally. | Project asset IDs include the checkout path and inventory file names. A second runner or an added manifest can sever history. Implicit baseline lookup deserializes up to 100 full reports per page and stops at 10,000 rows. Introduce stable external project identity separately from immutable artifact digest, and index latest eligible baseline. Plan a mapping for existing histories. |
| Policies and outputs | [Policy](../src/policy.rs) separates denial from operational failure, accepts exact scoped exceptions with expiry, and has independent missing-evidence guards. [Reports](../src/report.rs) and [integration payloads](../src/integrations.rs) support multiple consumers. | A CI denial or a generated provider payload does not stop a download. Policy outcomes need to be bound to identity, artifact digest, policy revision, advisory revision and an auditable enforcement decision. |
| API and operations | The HTTP service enforces input limits, bounds active scans and requires an authentication configuration for exposure beyond loopback. Monitor targets and notification retries have persisted state. | One SQLite connection and one configured bearer credential are a single trust domain. CPU-intensive scan work still runs in async request processing. No demonstrated tenant isolation, HA failover, restore objective or fleet throughput. [Monitor refresh](../src/main.rs) advances a synthetic generation; a due target is reevaluated even when advisory content has not changed. Webhooks can be delivered again if a claim expires before success is persisted; receivers need to deduplicate event IDs. |
| Delivery and tests | Locked Rust toolchain, dependency audit, CI coverage floor of 90%, signed Linux release packaging and verification. | Line coverage and signed artifacts establish neither scanner accuracy nor production behavior. Build and test the exact candidate image on the target platform; rehearse rollout and restore before cutover. |

Keep one deployable and the existing public CLI and report schema. The useful division is **input preparation → inventory/evidence evaluation → policy decision → persistence and delivery**. Keep OSV, SQLite, filesystems and repository enforcement at the edges. A Cargo workspace, new database or extra service should solve a measured deployment or resource constraint; the current file sizes alone do not justify one.

## What would count as an Xray replacement?

JFrog's own configuration distinguishes [repository indexing](https://github.com/jfrog/terraform-provider-xray/blob/852d1781e22c56dfabd65cef47087e77dc4b5796/docs/resources/binary_manager_repos.md), [watch scope](https://github.com/jfrog/terraform-provider-xray/blob/852d1781e22c56dfabd65cef47087e77dc4b5796/docs/resources/watch.md) and [policy actions](https://github.com/jfrog/terraform-provider-xray/blob/852d1781e22c56dfabd65cef47087e77dc4b5796/docs/resources/security_policy.md) such as blocking downloads, failing builds or blocking release-bundle promotion. These are distinct acceptance surfaces. Scope the target to the features the intended deployment actually uses.

| Cutover requirement | Current evidence | Acceptance before switching |
| --- | --- | --- |
| Packages, versions, dependency graph and licenses | 23 local manifest cases (20 projects, two SBOMs, one ZIP); no committed Xray captures. | Scan the same pinned real projects, SBOMs and images on both sides. Preserve tool versions, artifact digests, feed dates and omissions; review extra/missing packages per ecosystem. Include scoped packages, OS packages, image platforms and declared versus resolved versions. |
| Vulnerabilities and policy outcomes | OSV client, normalization, risk and exact exception tests; replay compares report-wide CVE sets without checking which package is affected. Two empty sets score 1.0. | Include known-positive and known-negative controls for each in-scope class. Compare the affected package **and version** as well as the advisory, severity, fix and resulting deny. Adjudicate every missed block with its owner; archive disagreement and intentional differences. |
| CI and repository enforcement | Local CLI emits exit codes and machine-readable outputs. No repository-side block path identified. | Start in observe-only mode. Test allow, deny, retry, duplicate events, stale/missing evidence, feed outage and recovery. Verify that a denied digest cannot be downloaded or promoted and that the old gate can be restored. |
| Re-evaluation of existing inventory | Scheduled local target scans, cursor and notification outbox. | Ingest one dated advisory change without modifying an artifact. Find affected digests, update decisions and deliver one observable event per transition. Measure time from feed ingestion to enforcement. |
| Scale, isolation and recovery | Local benchmark and single-process persistence. | Agree workload and budgets with the operator: package mix and sizes, ingest rate, cold/warm cache, concurrent writers/readers, p50/p95/p99 latency, peak RSS, disk growth and acceptable advisory age. Exercise restart mid-job, tenant boundaries and database restore, including policy and exception history. |

## Changes and how to verify them

- The [recording coverage gate](../tests/parity_recording_coverage.rs) makes incomplete comparisons visible. Use `hooray-parity check --require-recordings` with thresholds for a comparison run. The gate checks file coverage; it cannot authenticate a supplied capture or prove that an advisory provider ran. The default offline checks remain usable without a licensed instance.
- [Input preparation](../src/input.rs) now extracts archive members or applies OCI layers once per prepared input. Inventory, licensing and content scans share that view; expanded bytes are released before the advisory lookup. A controlled provider test removes a TAR after inventory is available and checks that the same file evidence is still stored. Automatic TAR classification can still read the input before preparation; live directories are not filesystem snapshots.
- The [graph](../src/graph.rs) uses the reverse edge index to avoid searching unrelated roots when enumerating paths. On the 256-tree fixture (eight nodes per tree, one leaf query per tree), the median for the batch fell from **57.11 ms to 0.455 ms** in five alternating release runs on an Apple M4 Max, Rust 1.90.0. The dense-graph case was 23.68 → 20.47 µs; an unchanged classification control was 5.61 → 5.71 µs. See [raw samples](measurements/graph-2026-11-20.json). Reproduce with `cargo bench --locked --bench performance -- --graph-only`. This is a path-query measurement, not whole-scan throughput.
- The [API database adapter](../src/api/database.rs) admits one operation before dispatching blocking work. A read cancelled while waiting no longer consumes a worker or executes later. Readiness reads the latest stored schema column instead of deserializing a report. A successful probe verifies database access and schema compatibility; it is not an integrity audit of all history. For one report with 8 MiB of metadata, 30 warmed loopback probes against debug builds went from 28.24 ms to 0.37 ms median. This measures readiness on that fixture, not general API throughput.
- The [Cargo parser](../src/parsers/cargo.rs) attributes a sibling manifest’s declared license to the matching local package in a multi-package lockfile. It leaves registry or mismatched packages unchanged. This can correct a policy decision; it does not change the dependency's license.
- The [dependency lockfile](../Cargo.lock) updates the affected SQLite, TLS, ZIP and Zstandard stacks. The project-specific BSD-2-Clause permission is limited to `zstd-sys`; its upstream notices ship in the archive and image. The unmaintained `chrono` dependency was removed; no advisory suppression was added. The [timestamp module](../src/timestamp.rs) keeps wire and SQLite timestamps separate from the clock used to run scans, and preserves leap-second ordering in policy and stored history. For Rust callers, `ScanRequest::as_of` and `OperationalRiskInput::as_of` now take `time::UtcDateTime`, `RiskInput::as_of` takes `time::Date`, and `Policy::evaluate` takes `time::OffsetDateTime`. Source callers must migrate; there is no database schema migration.

## Whole-scan performance

The [CLI benchmark](../scripts/bench_scan.py) starts a new release process, scans offline, evaluates policy, writes the report and creates a fresh SQLite database for each run. The two inputs each have 512 packages, 448 dependency edges and 512 license findings; the ZIP also has 32 source files. Both binaries produced matching normalized reports and persisted the expected run and finding count. Medians below are from five alternating pairs after a warmup on the same Apple M4 Max.

| Input | Wall time: upstream → candidate | Peak process memory: upstream → candidate |
| --- | ---: | ---: |
| CycloneDX SBOM | 63.91 → 65.05 ms (+1.8%) | 40.05 → 35.45 MiB (−11.5%) |
| ZIP with Cargo lockfile and sources | 63.32 → 67.03 ms (+5.8%) | 36.64 → 33.86 MiB (−7.6%) |

Both workloads used less memory. Neither showed a lower median wall time. Five local pairs establish a repeatable starting point, not a production latency distribution or a throughput target. [Individual samples and source/binary hashes](measurements/scan-2026-11-20.json) are committed. Run `python3 scripts/bench_scan.py` for the current build; add `--compare /path/to/baseline/hooray --compare-revision COMMIT` for the paired comparison.

## Candidate verification

- **Native build:** Rust 1.90.0, macOS arm64. All 850 tests passed with all targets and features; line coverage was 93.40% (90% required). Formatting and Clippy passed. Dependency advisories, bans, licenses and sources passed with five duplicate-version warnings.
- **Container:** A real Linux/arm64 build exposed an existing signed-`char` assumption in [the GitLab report publisher](../src/report.rs). Using the platform's C character type fixed compilation. The rebuilt image ran as UID/GID 1000 with the network disabled. A Cargo scan emitted all five GitLab artifacts; repeating it on the existing destination returned exit 2 and left all five file hashes unchanged. The image contained the three unmodified zstd-sys notices. The release workflow's TAR packaging step also preserved all three notices, the project license and the binary byte for byte (local archive layout check only). No release or remote CI run was triggered.
- **Own source:** The release CLI scanned this candidate's `Cargo.toml`, `Cargo.lock`, `LICENSE` and 60 Rust files under `src/` with the repository policy and a new database. It found 295 components and 744 edges. Policy returned exit 0: 295 license warnings and 12 allowed secret-rule findings. The run was offline; it made no vulnerability claim and did not include the intentionally malformed test corpus.
- **Replay control:** A clean copy of the 23-case corpus passed the local inventory checks. With `--require-recordings`, exactly 23 cases failed for missing recordings (exit 1).

## Live advisory control

On November 20, 2026, an online scan of the public npm corpus fixture produced 13 inventory components, 8 vulnerability findings and 13 license findings. The result included CVE-2020-8203; the allow policy returned exit 0. This checks the native CLI scan path against live OSV at one time. The OSV snapshot was not pinned and no Xray result was used.

## Recommended order of work

1. **Pick one real workflow.** Obtain the operator's Xray watch scope, policies, exceptions and a representative artifact set from one repository. Record which Xray features are in use, output expectations and current latency/volume. Store only approved, sanitized fixtures in this repository.
2. **Establish evidence.** Capture both sides at identified database revisions. Start with one known allow and one known deny, then add the positive/negative controls and image cases above. Use the strict coverage gate; keep offline scanner results separate from captures that exercised an advisory provider.
3. **Build indexing and decision history.** Add an artifact digest and stable project identity, an idempotent ingest queue, advisory revision tracking, selective re-evaluation and a per-digest policy decision. Prove recovery and unchanged-history behavior in tests before introducing repository enforcement.
4. **Run in parallel and cut over one repository.** Compare decisions and latency under representative load; give each unexplained difference an owner. Require a working rollback, restore, notification trace and operator acceptance. Expand to the next repository type only when its additional risks have fixtures and agreed limits.
